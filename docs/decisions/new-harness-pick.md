### D: The owner names the harness in each request

Status: Proposed 2026-11-09 in #179 (docs/roadmap/new-harness-adapter.md).

An agent runs every harness its laptop enables: those it found that the owner has not turned off
and that refuse nothing. The owner names one, signed, in each card run and each prompt, as the
repository is named (D-093): a line under the repository in the card's play menu, and a picker
beside it in the composer, from the harnesses the sealed setup answer lists (D-115), those that
take no cards greyed with the reason. There is no stored default and no per-project default; the
page remembers the last pick in the browser only. A session keeps the harness that started it, so
replies and fix rounds resume with it; another harness is a new conversation, never a switch. A
request from before the pick names none and runs on the host harness: Claude Code when the plugin
hosts, the first enabled harness when the daemon does. So do the turns nobody picks for: Check
again (D-116) and a proposal's draft (D-117). A request naming a harness the laptop has not enabled
fails with the reason. The server learns nothing: the name travels sealed, and the check-in's level
is the union over the enabled harnesses, with no name in it.

Cost: a page that never opened Settings asks the agent for its setup once per harness picker, a
sealed message in the direct chat. A reply after the owner turns the session's harness off fails
with that reason instead of moving to another harness.

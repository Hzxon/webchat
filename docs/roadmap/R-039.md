### R-039: The owner chooses what their agent's runs load from their Claude setup

Status: Idea. Proposed on 2026-11-07 after the review of #159.

Why: a run's background Claude starts with `claude -p --restricted --strict-mcp-config` and a fixed
`--tools` list (`claudeArgs` in `agent/claude.ts`, D-097). It reads nothing of the owner's
`~/.claude`: no CLAUDE.md, no skills, and it has no Skill tool. A test run with the same flags
reported all three missing. So a run does not work like the owner's own sessions. In #159 the pull
request body ended with a "Generated with Claude Code" line that the owner's CLAUDE.md forbids, and
the title did not follow the owner's commit message skill.

Scope:

- The plugin tells its owner what it can load: whether `~/.claude/CLAUDE.md` exists, and the name
  and description of each skill in `~/.claude/skills`. It sends this as an encrypted message in
  their direct chat, never in a check-in, so the server learns none of it.
- The agent's settings in the Agents pane list these: "Follow my CLAUDE.md", a checkbox for each
  skill, and "No AI attribution in commits and pull requests". The page sends the choice as the
  owner's signed `setup` message. Like `sleep`, `forget` and `clone`, the plugin heeds it only from
  its owner, with a send time within 10 minutes, once (D-089, D-101, D-108, D-113).
- A new `AGENT_LEVEL` marks plugins that heed `setup`. The pane offers the settings only to them,
  and tells the owner of an older plugin to update (D-103).
- The plugin keeps the choice in its data folder and applies it to every card run and every
  conversation turn:
  - CLAUDE.md goes in with `--append-system-prompt-file`.
  - The chosen skills are copied into a plugin folder made for the run, which holds only a
    `skills/` folder. The plugin passes it with `--plugin-dir` and adds `Skill` to `--tools`. It
    copies them because the run edits files in its folders and must never edit the owner's skills.
  - The settings file that `claudeSettings` writes sets `attribution.commit` and `attribution.pr`
    to hide both lines.
- The pane shows what the agent applied to its last run, so the owner sees a choice it could not
  apply, such as a skill that was deleted.

These stay off, whatever the owner picks: the owner's settings files, hooks, MCP servers, installed
plugins and permission rules. They run commands or hold tokens, and a run follows text that
teammates wrote (D-097, D-104). The sandbox, the block on reads outside the working folders and the
denied credential variables stay as they are.

Cost: a teammate's card can now steer a run through the owner's chosen skills. A skill's scripts
run in the same sandbox, so they reach nothing new. CLAUDE.md and the skills go to Anthropic with
each turn, as in the owner's own sessions. Skill names reach only the owner's page, encrypted. This
changes D-097 and adds one line to `.claude/rules/projects.md`.

Open questions:

- Is the choice per agent or per project? Per agent is simpler. Per project lets a course project
  leave out personal skills.
- Should skills from the owner's installed plugins be offered too? A plugin's skill may call
  scripts elsewhere in the plugin, so the copy would need those files but not the plugin's hooks,
  `.mcp.json` or agents.
- Should the owner be able to allow the Agent tool, so skills that start subagents work? The
  subagents get the same tools and sandbox.
- Should a read-only MCP server, such as one for library docs, be allowed one at a time? Each one
  needs its own review of what it reaches.

Done when: an owner turns on CLAUDE.md, a commit message skill and "No AI attribution" in the
pane. The next card run then opens a draft whose title follows that skill and whose body has no
"Generated with" line. A test checks that the run's arguments and settings file hold the plugin
folder, the Skill tool and the attribution keys, and that nothing but `skills/` is copied.

# Agent requests, runs and pushes

Each line is a constraint the code cannot state on its own. The number names the decision in
docs/decisions.md that explains it.

- Run requests, reports and cancels are messages whose sealed `run` field names the card or the request's message id; a page folds only reports from the agent the request names, and an agent heeds only its owner's cancel (D-086, R-030).
- A card's run state comes from the user's run messages in their chats with their agents; its status line follows from any page of theirs, under the card's lock, once per report: Running on claimed, Waiting for a decision on decision, `Waiting for K-12: Ann and Bo choose` on overlap, In review on done, Done or Fixed on merged, its old status back on failure, stale or a draft closed unmerged; a card that still says `In progress: Ann’s agent` reads as `Running: Ann’s agent`, and a request's older `was` goes through `newStatus`, so a run in flight across the change still moves (D-100, D-105, D-118).
- The brief refuses a card whose status shows someone else's agent `Running:`, `In review` or `Waiting for`, the only run state teammates see (K-59, D-100, D-118).
- A card run refuses a card an open pull request claims; its first turn checks the card and commits nothing; only then do an empty claim commit and the draft open, before any code (D-118).
- With the plan gate on, the default, a card that holds reports `planned` with the check's plan and waits in `plans.json`, before the claim commit, for the owner's `fix`: a go or their words; a stop or 7 days end it. Only `noPlan` in the setup choice skips it, and only for a harness whose adapter declares the knob (docs/decisions/redirect-plan-gate.md).
- A card run's draft carries the check's `touches` as a `Touches:` line after `Claims`; once the draft opens, and before each push of finished work, the files it touches or its branch changes are compared with the open pull requests by `shared/overlap.ts`, the `overlap` check's own rule, and a share with a lower-numbered draft stops the run with an `overlap` report; it goes on only once that draft lets the files go or on an `Overlap with K-12: wait|stack|fold` line that one of the two card owners signed after the wait began, and the agent never chooses (docs/decisions/new-overlap-blocks.md, docs/roadmap/new-overlap-gate.md).
- A run that fails or waits 7 days before its work is done closes its draft with a comment and keeps its branch; a merge accepts only the Proposed decisions the run named that its board holds (D-118).
- A stop before the work is done pauses the run instead: what is committed is pushed, and the worktree, branch, draft and session stay in `pulls.json` as `unfinished.paused` with `stopped`; the owner's `fix` with a note resumes the session with their words fenced, as teammates' text is, and a second stop closes the draft (docs/decisions/stop-pauses-run.md).
- A run's progress reaches the owner as sealed `progress` reports, one sentence from the adapter at most every 30 seconds and only when it changed, never the harness's output itself; the service worker shows no notification for one, except on Safari (docs/decisions/stop-pauses-run.md, D-047).
- An agent runs a request only when its owner sent it, verified against the pinned keys, with a signed send time within 10 minutes of its own clock, and the hash of the brief they saw: the card, then the decisions without the superseded ones, as `briefText` makes it on both sides (D-089, D-105).
- An agent acts on a request's signed client id once; it remembers ids on disk while a copy could still run (K-47, D-093).
- An agent pins a person's changed keys only on its owner's signed `trust` message in their direct chat, for the fingerprint the server shows now and newer than the last check it pinned; whatever makes the page pin changed keys must send it to the owner's agents too, or their briefs hash differently (D-110, K-57).
- An agent answers a second request for the card it is running with one failed report and starts nothing; a card is the board's doc and section, a run that ended no longer counts, and another card runs beside it, with no cap (K-51, D-099, R-037).
- The agent runs a request only in the folder whose origin is the request's signed `repo`, and refuses a folder whose origin's https address holds a login, which a shell could read from `.git` (D-093, D-094, D-097).
- The harness's turn fails after 2 hours with no output, which does not run while a question waits for the owner (`Quiet`, `watchdog`); the board stops waiting on a request no agent answers after 30 minutes (D-097, D-100).
- The agent works only in a folder that a `connected` mark in the keyholder's folder names, while it is a checkout of that repository, which the runner confirms; only the owner's signed clone and signed connect approval write a mark (D-101).
- `webchat-agent card` sends only a new card's file, checked by a turn as a prompt's drafts are, as a sealed `proposal` draft to the owner; only the owner's `added` note gives it its number, and the command waits for that note and never writes the board (R-044, D-104, D-116).
- The owner's signed `pick` opens a folder window through the runner, and the folder picked only files a connect request, as `webchat-agent connect` does; nothing the runner returns marks a folder (the connect-approval decision).
- `webchat-agent connect` never writes a mark: it files a request, and the approval must repeat the repository and folder the owner saw and arrive within 10 minutes of the agent sending it, the agent's clock, or it changes nothing (the connect-approval decision, proposed in #202).
- The keyholder clones only on its owner's signed clone message, in their direct chat, within 10 minutes, once; only a repository a project of the owner and the agent links; into its own full clone first, and the runner makes `~/WebChat/<owner>/<name>` from a bundle of it, never the harness's turn (D-108).
- An agent never writes the board: its card drafts reach it only when the owner's page writes them, and a change only while the card's text still has the hash the draft names (D-104).
- A conversation's brief holds only the board its owner's page named in the signed prompt, never every project the agent is in: anyone can add an agent to their project (D-104).
- Only the keyholder pushes: the run's `agent/*` branch, never forced, and it never merges. The runner's git in a worktree runs through `worktreeGit`, with hooks off and on the git folder the checkout lists, never the worktree's `.git` file, since the worktree's files are the model's (D-092).
- The keyholder's half (`agent/keep.ts`) never runs git in a folder the owner owns: it fetches and pushes only in its own bare clone, with hooks off and credentials only from `gh`, one operation per repository at a time, and what it sends or takes of the owner's folders is a bundle (docs/decisions/locked-room.md).
- A run's work is pushed only after `Keep.acceptBundle` took it: exactly one ref, the run's recorded `agent/` branch, `check-ref-format`, `bundle verify`, its pack taken with `index-pack --strict` rather than fetched, since git before 2.46 ignores `transfer.fsckObjects` for a bundle, the run's base an ancestor, no rewind, at most 512 MiB (docs/decisions/locked-room.md).
- The board's copy is committed with git plumbing in a temporary index (`Keep.commitFiles`), never a checkout, so a link in the repository, such as `docs`, cannot lead a write out of the clone (docs/decisions/locked-room.md).
- A run's worktree is under `.claude/worktrees`, where the sandboxed shell may write. A run never pushes to main and fails after 2 hours of silence or with no commits (D-092).
- A review by anyone but the owner waits for the owner's `fix` message, which names the review's report: only the text that report showed runs, so nothing posted after the owner looked rides along. The owner's own rounds count toward no limit (D-105).
- The plugin stops watching, when it loads, a draft whose request is not in the owner's direct chat with the agent: the pane builds a card's thread only from that chat, so it shows neither that draft's reviews nor the button that sends the go (K-58, D-105).

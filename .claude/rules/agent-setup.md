# Agent accounts, setup, the locked room and the updater

Each line is a constraint the code cannot state on its own. The number names the decision in
docs/decisions.md that explains it.

- An agent is a member account that never makes keys; it keeps its secrets in the role account's folder (`/var/webchat`, `/var/lib/webchat`), one copy for the laptop under `laptop/`, behind the one `watch.lock` that the serving keyholder holds (D-085, D-094, docs/decisions/locked-room.md).
- The keyholder (`agent/index.ts keyholder`) is the one host of `Plugin`, and `dev` runs it with a runner in one process; `plugin.ts` never names a harness or a command of its host, and `serve`, `pair <code> <name>` and the plugin's server are gone (docs/decisions/one-daemon-host.md).
- An agent checks in every 15 seconds, and every 60 once an hour passes with no request, run or turn (`checkInEvery`); the server counts an agent online for 2 minutes after a check-in, a person for 1, in `toUserDTO` and in the fingerprint alike (docs/roadmap/new-agent-setup.md).
- `webchat-agent setup` checks the administrator rights first and stops before it changes anything; its other checks are read-only, and it changes something only after its one question, asked on `/dev/tty`, since the line runs under `curl … | sh` and stdin is the script (docs/decisions/agent-install.md).
- Setup never changes a security setting: for WSL2 without systemd, and for Ubuntu's AppArmor rule on user namespaces, it prints the fix, and it installs only git, the sandbox's `bubblewrap` and `socat`, and the harness's own installer (docs/decisions/agent-install.md).
- Setup pairs before it installs anything, since a pairing code lapses after 10 minutes and Apple's installer can take longer; a run with no code pairs nothing and replaces the services (docs/roadmap/new-agent-setup.md).
- The runner's login service runs `<installed program> runner` with the PATH an interactive login shell has, read between markers so a profile's output cannot spoil it; a value in a unit or a plist goes through `systemdUnit` or `launchdPlist`, which escape `%`, `$` and XML (docs/roadmap/new-agent-setup.md).
- An agent's account comes only from pairing: the code stays in the page and the agent, the server sees its SHA-256 and HMAC proofs, and each side pins the keys the code proved (D-093).
- The picks at pairing are one `picks` field sealed under a key from the pairing code, with the agent's keys as its AAD; the server never holds a harness name, and the agent writes `linked` only once the owner approved (docs/decisions/harness-linking.md).
- Nothing secret crosses the keyholder's socket (`agent/room.ts`) and nothing on it carries authority, since any process of the owner can connect: every reply is checked as data (harness names against `SUPPORTED`, folders against the request, branches and worktrees against the card, answers with `fits`, bundles with `acceptBundle`), and the `approve` the runner sends only reaches the keyholder's own caps and question (docs/decisions/locked-room.md).
- The first runner to say hello keeps the socket; a second is refused while it is open, and a version that differs is refused, except the updater's hello, which skips the check and may ask only `busy`. Lines are capped at 4 MiB, and a transfer id is good once, for 10 minutes (docs/decisions/locked-room.md).
- Pairing never crosses the socket: a code from another WebChat account would make that account the agent's owner. The keyholder shows offline, with no check-ins, while no runner is connected (docs/decisions/locked-room.md).
- The rulebook runs in the runner (`LocalBench.turn`), where the owner's paths resolve; the keyholder's `Permits` only caps, grants and asks (docs/decisions/locked-room.md).
- The keyholder runs only programs that root owns: Apple's command line tools git or `/usr/bin/git`, and the `gh` release that setup pins by SHA-256 in `agent/gh.ts` and installs in the root-owned program folder; its PATH lists only root-owned folders, never Homebrew's (docs/decisions/locked-room.md).
- Setup's root commands write generated content through stdin into a folder only root writes, by a rename (`put`, `putAs` in `agent/lockroom.ts`), never through a file the owner could swap; the program is installed from bytes hashed against the hash setup took at its start; every root command goes through one `Root`, which tests replace (docs/decisions/locked-room.md).
- Only setup's sudo pairs the keyholder: `webchat-agent pair` takes the code and picks on stdin, never in an argument, and refuses to run as anyone but the role account; setup deletes `_webchat` and its groups only when the mark in their full name or comment is its own, and refuses a foreign one. One owner per laptop: `_webchatipc` holds only them (docs/decisions/locked-room.md).
- The keyholder starts only after `selfProblem` (`agent/lockroom.ts`): it runs as the role account, its data folder is its own with mode 700, and its program, `git` and `gh` are root-owned and writable by no one else, up every parent folder; it sets umask 077 (docs/decisions/locked-room.md).
- `status` over the socket answers fields (`AgentStatus`), and `doctor` and setup read them, never the text; a field the agent cannot know yet is left out, not guessed (docs/decisions/locked-room.md).
- The updater (`agent/update.ts`) runs as root from the root-owned program and trusts only what root owns: `update.json`, which setup wrote through stdin, and the release address pinned in `AGENT_RELEASES`, never one the server names. The server only says which release; a release that is not `x.y.z` is refused before any plan is built, and one not newer than the program does nothing (docs/decisions/agent-self-update.md).
- The updater never uses a GitHub login and never opens the role account's files. A download is checked in memory against its `.sha256`, unzipped and probed with `--version` into the program's folder, and renamed into place; a failure keeps the old program and restarts nothing (docs/decisions/agent-self-update.md).
- The updater restarts the keyholder only when it reports nothing running, or after 24 hours busy; it keeps the old program until the new keyholder answers with the new version in 2 minutes, else it puts it back and skips that release. Setup and uninstall stop it first (docs/decisions/agent-self-update.md).
- The keyholder service never exits on a refused sign-in: `Plugin.serve` idles with the problem, since launchd restarts it every 10 seconds and each failed sign-in uses up the address's limit that the next pairing needs (D-068, docs/roadmap/new-removed-agent-restart.md).

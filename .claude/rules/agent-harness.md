# Harnesses and linking

Each line is a constraint the code cannot state on its own. The number names the decision in
docs/decisions.md that explains it.

- The owner names the harness, signed, in each run request and prompt, from the sealed setup answer's list; the keyholder keeps no default, runs a request that names none on the first harness the owner linked, fails one naming a harness that is not linked with the reason, and resumes every reply and fix round with the harness that started the session, which `Conversation` and `Watched` record by name (docs/decisions/new-harness-pick.md).
- Only a harness the owner linked runs: `SetupChoice.linked`, in the order they linked, minus the older `off`, which a page from before linking still writes and which the merge in `setupOnWord` keeps; the first start of an agent with no `linked` links what it found minus `off`, and nothing later links itself (docs/decisions/harness-linking.md).
- The check-in's level is `answers | setup`, plus `cards` from `noHarness()` over the linked harnesses alone, so with none linked it keeps the first two and every request fails with `NONE_LINKED`; test an empty list apart, since `every` is true for it (docs/decisions/harness-linking.md).
- A request from `webchat-agent link` or `connect` is a request over the keyholder's socket, which it files in `asks/` and sends as a sealed `ask`: a file older than 10 minutes, a name outside `SUPPORTED`, and a second request for what waits are dropped, and the approval acts only on what the agent recorded for that client id, on the owner's word in their direct chat, signed within 10 minutes, once; the next `ask` kind adds a variant of the same field (docs/decisions/harness-linking.md).
- The finder looks only in absolute folders: the PATH the process has and a few in the home folder; a relative one would be a place the model writes (D-097, docs/decisions/harness-linking.md).
- A harness adapter refuses a version below its minimum from one `--version` read per adapter, which the finder rebuilds when the program or its mtime changes; Claude Code's is 2.1.259, the first with `--permission-prompts` and `--permission-prompt-tool`, and Codex has none (docs/decisions/harness-linking.md).
- For Claude Code, the harness's turn always runs `claude -p --input-format stream-json --restricted`, one process for a session with the plugin's `--settings` file, which the runner writes again before each process starts, since it sits in the owner's folder, which keeps `sandbox.failIfUnavailable`, `permissions.blockReadsOutsideWorkingDirectories` and a `deny` for each credential variable: a plain `-p` run loads the repository's hooks and `.mcp.json`, an unavailable sandbox runs the shell unsandboxed, a sandboxed shell reads the macOS keychain, and it inherits every token in the environment, and Claude Code's `session-env` holds the SessionStart hooks' environment. Never set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` there: it makes every sandboxed command ask (D-097).
- Text a teammate wrote reaches the harness's turn only on its stdin, never in its arguments, which `ps` shows (D-097).
- A harness adapter (`agent/harness.ts`) owns the turn, its warning and the setup it offers; `plugin.ts` never names a harness (docs/roadmap/new-harness-adapter.md).
- An ACP agent runs only from `agent/acp-agents.ts`, whose entries carry a file name (never a path, `npx` or another launcher), the args that make it speak ACP, and the args or environment that skip the owner's settings and MCP servers with a dated check; the list-shape test in `test/acp.test.ts` refuses an entry without them, unless `HARNESS_WARNING` in `shared/types.ts` names it, as for Hermes, whose warning setup, the link approval and Settings show; `{data}` in an isolation arg is the agent's own folder in the runner's, and a turn is refused while a `refuseFiles` entry exists in the working folder, checked before every turn; nothing else may supply a command (docs/decisions/acp-adapter.md, docs/decisions/new-hermes-unconfined.md, docs/decisions/new-antigravity-harness.md).
- An ACP turn's text goes only over the protocol, and its answer comes only from `submit_answer`, which `fits` checks against that turn's schema; its permission requests get `judge`'s answer, never an `*_always` option, and what the rulebook cannot decide goes to the owner when the turn can ask (docs/decisions/acp-adapter.md, docs/decisions/harness-approvals.md).
- An adapter that keeps a process for a session ends it after 10 minutes without a turn, in `end(session)` and when the daemon exits; a later turn resumes the session (docs/decisions/acp-adapter.md).
- Every harness may take cards: its adapter's `refusal()` says only why this laptop cannot run it, and `warning()` says what its sandbox lets its shell read, which shows in its row's `attention` and stops nothing. Codex cannot commit, so the runner commits what it left, titled with the answer's title; it runs one `codex app-server` per session with each of the owner's MCP servers off by name (`-c mcp_servers.<name>.enabled=false`; `-c` merges and never replaces), hooks off and `shell_environment_policy.inherit="core"`; its `.rules` still load, and its message goes over the protocol (docs/decisions/harness-rulebook.md, docs/decisions/harness-approvals.md).
- A run loads of the owner's Claude setup only what their signed `setup` chose: CLAUDE.md through `--append-system-prompt-file`, and copies of chosen skills, never links in them, in a plugin folder made for the turn that holds only `skills/`; never the owner's settings, hooks, MCP servers, plugins or permission rules. Attribution goes in the object form only, since a `-p` run drops a settings file that fails validation. The level is a set of bits: test cards with `runsCards` and settings with `takesSetup`, never with `>=` (D-115).
- A harness adapter declares a knob only when it honors it with no code outside the sandbox and no change of permission or sandbox mode; permission mode, plugins, hooks and MCP servers are never knobs, for any harness, except `own`, which says the adapter can run a session in the owner's whole setup (D-157). What a harness is and offers reaches only its owner, sealed in `setupState` (D-115).
- A harness's `refusal` in `setupState` says why it runs nothing, and `answers` says the same; the sandbox warning goes in `attention`, which pages from before linking ignore (docs/decisions/harness-linking.md).
- Own setup (`Turn.own`) runs only a conversation whose signed prompt says `own`, which only the pane's typed question sets, while the owner's signed `SetupChoice.own` names that harness and its adapter offers the `own` knob: never a card run, a fix round, Check again or `webchat-agent card`. It works in the connected folder, never in a scratch copy, and never stores that folder as `scratch`, which an ended conversation removes; a reply after the switch changed fails rather than move the session, and only a signed hand over's `own` moves a conversation to the other setup, as a new session from the summary (D-157, docs/decisions/new-setup-switch.md).
- An own-setup turn loads nothing of WebChat's: Claude Code runs `-p --input-format stream-json` with no `--restricted`, `--settings`, `--tools`, `--strict-mcp-config`, permission mode or copied setup, and only the approval endpoint joins, to ask the owner; Codex runs a bare `codex app-server` and its `thread/start` names only the folder, the model and, for Plan first, the `read-only` sandbox; the rulebook does not judge its asks (D-157, docs/decisions/new-codex-own-setup.md).
- Codex's models are what its own `model/list` shows, minus hidden ones, read by a short-lived app-server with the restricted arguments when the agent looks for harnesses, with each model's efforts as it lists them and the default model's under `''`, the effort sent on `turn/start`; with none read, it offers no models or efforts and runs Codex's default (docs/decisions/new-codex-own-setup.md).

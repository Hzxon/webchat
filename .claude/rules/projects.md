# Projects, channels, groups, docs, the board and agents

Each line is a constraint the code cannot state on its own. The number names the decision in
docs/decisions.md that explains it.

- Every project member is a member of every channel; there are no private channels (D-024).
- A new channel's key is wrapped for exactly the project's members at that moment; adding people brings every channel's current key wrapped for each of them, checked under the project's row lock (D-025).
- A stale view answers `409 stale_project` or `409 stale_group`; the page reloads and retries once, and shows a second conflict as an error (D-025, D-039, D-043).
- The member who adds people wraps its own opened copy of each key; each key holds the one it replaced so newcomers read history, and their read pointers start at the newest message (D-026, D-043).
- Adding people to a group: at most 20 at once; the server checks under the group's lock that the copies cover exactly those added, the key they came from is current and the adder is a member (D-043).
- Adding people to a project also checks under the lock that the adder is still a member (D-043).
- A group from before encryption with no key takes members without a key copy; its first message keys it for everyone (D-043).
- Channel names go through `toChannelName` and `isChannelName` in `shared/types.ts` on both sides: lowercase letters and digits in any script, single hyphens, at most 40 characters, unique per project (D-027, D-065).
- `toChannelName` applies NFKC first, cuts to the limit before trimming hyphens, and counts UTF-16 units like the server (D-065).
- Only the owner removes people, deletes or hands over; `projects.created_by` and `conversations.created_by` name the owner, the API calls it `ownerId`, and a group with no owner is open to any member (D-039, D-045).
- Only the owner deletes a channel, under the project's lock, and never #general: pages take the project's oldest channel for it, and its key opens the docs (D-081, D-096).
- Removal gives every chat in the project or group a new key for exactly those who stay, in the removing request (D-039, D-044).
- A project or group always has an owner among its members: the owner hands over before leaving, and the last member of a group deletes it (D-045).
- Only a person owns a project or group, never an agent: the dialog offers no "Make owner" for one and the server refuses it (D-114).
- Of being added, removed, leaving and handing over, only being added sends a notification (D-031, D-039, D-045).
- Docs exist only in a channel, keyed by #general; a revision is sealed under the `webchat/doc/v1` header binding chat, key id, author, doc and section (D-081).
- A section save needs its `doc_locks` lock, which lapses 2 minutes after the last check-in; doc versions and held locks are in the sync fingerprint (D-081, D-021).
- A board is two docs marked by a `board` field inside the sealed title; a card's number, title and status come from its first two lines, in the `docs/decisions.md` format (D-082).
- A page gives a new card its number only through `addCard` in `client/src/docs.ts`: under the lock of its column doc's `title` section, from the cards loaded under that lock, never from cards it loaded before (D-116).
- A draft's `related` ids are only ones the brief held: its cards, the decisions the team holds and the open pull requests the plugin listed; the page drops a card or decision it cannot find (D-116).
- Only the project's owner links its board: the link is the `repo` of the Roadmap doc's sealed title, and the page and the agent count it only when the owner wrote that title; the agent copies only boards of projects its owner owns, and one board per repository (D-117).
- A board's copy is `copyOf` in `shared/board.ts`, for Copy as Markdown and for the agent alike; the agent pushes only `agent/board`, never forced, writing the two docs and removing the proposal files its owner added (D-117, D-092).
- A Bark push carries chat name, sender name, urgency and unread count, never message text; one APNs provider token is shared through the database and refreshed at most every 20 minutes (D-054).
- The Bark key comes from `BARK_APNS_KEY` and is never committed (D-054).
- An agent is a member account that never makes keys; it keeps its secrets in `~/.webchat/<name>/account.json` or the plugin's data folder, and two agents must not share that file, so the plugin keeps one copy for the laptop under `laptop/`, behind the one `watch.lock` that the serving window holds (D-085, D-094).
- The daemon (`agent/index.ts serve`) and the plugin (`agent/mcp.ts`) are two hosts of one `Plugin`, each with a data folder of its own, so never point both at one; a host builds the harness and `plugin.ts` never names a host (the daemon-host decision, proposed in #177).
- An agent's account comes only from pairing: the code stays in the page and the agent, the server sees its SHA-256 and HMAC proofs, and each side pins the keys the code proved (D-093).
- Run requests, reports and cancels are messages whose sealed `run` field names the card or the request's message id; a page folds only reports from the agent the request names, and an agent heeds only its owner's cancel (D-086, R-030).
- A card's run state comes from the user's run messages in their chats with their agents; its status line follows from any page of theirs, under the card's lock, once per report: In progress on claimed, Waiting for a decision on decision, In review on done, Done or Fixed on merged, its old status back on failure, stale or a draft closed unmerged (D-100, D-105, D-118).
- The brief refuses a card whose status shows someone else's agent `In progress:`, `In review` or `Waiting for a decision`, the only run state teammates see (K-59, D-100, D-118).
- A card run refuses a card an open pull request claims; its first turn checks the card and commits nothing; only then do an empty claim commit and the draft open, before any code (D-118).
- A run that fails, is stopped or waits 7 days for a decision before its work is done closes its draft with a comment and keeps its branch; a merge accepts only the Proposed decisions the run named that its board holds (D-118).
- An agent runs a request only when its owner sent it, verified against the pinned keys, with a signed send time within 10 minutes of its own clock, and the hash of the brief they saw: the card, then the decisions without the superseded ones, as `briefText` makes it on both sides (D-089, D-105).
- An agent acts on a request's signed client id once; it remembers ids on disk while a copy could still run (K-47, D-093).
- An agent pins a person's changed keys only on its owner's signed `trust` message in their direct chat, for the fingerprint the server shows now and newer than the last check it pinned; whatever makes the page pin changed keys must send it to the owner's agents too, or their briefs hash differently (D-110, K-57).
- An agent answers a second request for the card it is running with one failed report and starts nothing; a card is the board's doc and section, a run that ended no longer counts, and another card runs beside it, with no cap (K-51, D-099, R-037).
- The plugin runs a request only in the folder whose origin is the request's signed `repo`, and only while the harness's turn keeps the secrets from its shell. It refuses runs in a folder whose origin's https address holds a login, which the shell could read from `.git` (D-093, D-094, D-097).
- The harness's turn fails after 2 hours with no output; the board stops waiting on a request no agent answers after 30 minutes (D-097, D-100).
- The plugin works only in a folder that a `connected` mark names, while it is a checkout of that repository; only the `connect` tool and the owner's signed clone write a mark, and that tool keeps `requiresUserInteraction`, so the owner approves every call (D-101).
- The plugin clones only on its owner's signed clone message, in their direct chat, within 10 minutes, once; only a repository a project of the owner and the agent links; only into `~/WebChat/<owner>/<name>`; and with its own `gh`, never the harness's turn (D-108).
- For Claude Code, the harness's turn always runs `claude -p --restricted` with the plugin's `--settings` file, which keeps `sandbox.failIfUnavailable`, `permissions.blockReadsOutsideWorkingDirectories` and a `deny` for each credential variable: a plain `-p` run loads the repository's hooks and `.mcp.json`, an unavailable sandbox runs the shell unsandboxed, a sandboxed shell reads the macOS keychain, and it inherits every token in the environment, and Claude Code's `session-env` holds the SessionStart hooks' environment. Never set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` there: it makes every sandboxed command ask (D-097).
- Text a teammate wrote reaches the harness's turn only on its stdin, never in its arguments, which `ps` shows (D-097).
- A harness adapter (`agent/harness.ts`) owns the turn, the isolation proof and the setup it offers; `plugin.ts` never names a harness (docs/roadmap/new-harness-adapter.md).
- A conversation's messages carry a sealed `prompt` field naming its prompt's client id, never the server's message id; the plugin heeds only its owner's, in their direct chat with the agent, with a signed send time within 10 minutes and once per client id (D-102, D-089, K-47).
- A conversation's turns run in a scratch repository of its own in the temp folder, never a worktree of the owner's checkout, whose `.git` it would share; nothing from it is pushed. A question with no repository runs in an empty folder there, from the board alone (D-102, R-038).
- The plugin forgets a folder only on its owner's signed `forget` message in their direct chat, and removes its mark, never its files (D-101).
- While the plugin's `asleep` file exists, no window takes `watch.lock` and the serving one starts nothing new; only the owner's signed `sleep` message or `/webchat:sleep` writes it, only `/webchat:wake` removes it, and a background job (`CLAUDE_JOB_DIR`) never serves (D-113).
- The page asks only a session whose check-in names `AGENT_LEVEL.answers` or above: older plugins check in but ignore prompts, so the pane tells their owner how to update instead (D-103).
- A run loads of the owner's Claude setup only what their signed `setup` chose: CLAUDE.md through `--append-system-prompt-file`, and copies of chosen skills, never links in them, in a plugin folder made for the turn that holds only `skills/`; never the owner's settings, hooks, MCP servers, plugins or permission rules. Attribution goes in the object form only, since a `-p` run drops a settings file that fails validation. The level is a set of bits: test cards with `runsCards` and settings with `takesSetup`, never with `>=` (D-115).
- A harness adapter declares a knob only when it honors it with no code outside the sandbox and no change of permission or sandbox mode; permission mode, plugins, hooks and MCP servers are never knobs, for any harness. What a harness is and offers reaches only its owner, sealed in `setupState` (D-115).
- An agent never writes the board: its card drafts reach it only when the owner's page writes them, and a change only while the card's text still has the hash the draft names (D-104).
- A conversation's brief holds only the board its owner's page named in the signed prompt, never every project the agent is in: anyone can add an agent to their project (D-104).
- In the plugin only the server pushes: the run's `agent/*` branch, never forced, and it never merges. Its git in a worktree runs with hooks off, since the worktree's files are the model's (D-092).
- A plugin's worktree is under `.claude/worktrees`, where the sandboxed shell may write. A run never pushes to main and fails after 2 hours of silence or with no commits (D-092).
- A review by anyone but the owner waits for the owner's `fix` message, which names the review's report: only the text that report showed runs, so nothing posted after the owner looked rides along. The owner's own rounds count toward no limit, and the daemon takes no cards (D-105).
- The plugin stops watching, when it loads, a draft whose request is not in the owner's direct chat with the agent: the pane builds a card's thread only from that chat, so it shows neither that draft's reviews nor the button that sends the go (K-58, D-105).

# Projects, channels, groups, docs, the board and agents

Each line is a constraint the code cannot state on its own. The number names the decision in
docs/decisions.md that explains it.

- Every project member is a member of every channel; there are no private channels (D-024).
- A new channel's key is wrapped for exactly the project's members at that moment, by someone still among them; adding people brings every channel's current key wrapped for each of them, checked under the project's row lock (D-025).
- A stale view answers `409 stale_project` or `409 stale_group`; the page reloads and retries once, and shows a second conflict as an error (D-025, D-039, D-043).
- The member who adds people wraps its own opened copy of each key; each key holds the one it replaced so newcomers read history, and their read pointers start at the newest message (D-026, D-043).
- Adding people to a group: at most 20 at once; the server checks under the group's lock that the copies cover exactly those added, the key they came from is current and the adder is a member (D-043).
- Adding people to a project also checks under the lock that the adder is still a member (D-043).
- A group from before encryption with no key takes members without a key copy; its first message keys it for everyone (D-043).
- Channel names go through `toChannelName` and `isChannelName` in `shared/types.ts` on both sides: lowercase letters and digits in any script, single hyphens, at most 40 characters, unique per project (D-027, D-065).
- `toChannelName` applies NFKC first, cuts to the limit before trimming hyphens, and counts UTF-16 units like the server (D-065).
- Only the owner removes people, deletes or hands over; `projects.created_by` and `conversations.created_by` name the owner, the API calls it `ownerId`, and a group with no owner is open to any member (D-039, D-045).
- Only the owner deletes a channel, under the project's lock, and never #general: pages take the project's oldest channel for it, and its key opens the docs (D-081, D-096).
- Removal gives every chat in the project or group a new key for exactly those who stay, in the removing request (D-039, D-044).
- A project or group always has an owner among its members: the owner hands over before leaving, and the last member of a group deletes it (D-045).
- Only a person owns a project or group, never an agent: the dialog offers no "Make owner" for one and the server refuses it (D-114).
- Of being added, removed, leaving and handing over, only being added sends a notification (D-031, D-039, D-045).
- Docs exist only in a channel, keyed by #general; a revision is sealed under the `webchat/doc/v1` header binding chat, key id, author, doc and section (D-081).
- A section save needs its `doc_locks` lock, which lapses 2 minutes after the last check-in; doc versions and held locks are in the sync fingerprint (D-081, D-021).
- A board is two docs marked by a `board` field inside the sealed title; a card's number, title and status come from its first two lines, in the `docs/decisions.md` format; pages write `Ready` and `Running:`; `readCard` alone reads the older `Next` and `Planned` as `Ready` and `In progress` as `Running`, keeping the rest of the line, so no other code tests the old words (D-082, the board-lanes decision, proposed in #188).
- A card's opener is the author of its section's oldest revision, and only when that revision's sealed content says `opened`, which `addCard` alone writes (the board-lanes decision, proposed in #188).
- A card with an owner shows the newest member's revision whose status its author may set (`standing`), and only its owner's removal stands; Roadmap cards are read through `boardCards` and written through `rewriteCard` or `takeCard`, from the card's `text`, the text that stands; `written` is only for hashes (the card-owner decision, proposed in #189).
- A run, a claim or a take starts only where `startable` allows: a Ready card, an Open one with no owner, or the user's own pick (the card-owner decision, proposed in #189).
- A card changes owner only through `takeCard`, where `startable` allows (the card-owner decision, proposed in #189).
- A request on a card goes to the person asked as a message in the asker's direct chat with them, with a sealed `card` field, so it pushes only them (the card-notes decision, proposed in #189).
- A review verdict counts only while its reviewer's own newest revision holds the line and is newer than the owner's or the owner's repeats it, and an answer to a change only from the owner's (`reviewsOf`); moves, drafts, run reports and a hand edit keep the review lines that stand, the edit through `keepReviews` from the lines read under its lock, so only the buttons change a review; while a verdict stands, a word of anyone else's stands only in Open, as a merge, or with an In review status a verdict's word says (the card-review decision, proposed in #190).
- A page gives a new card its number only through `addCard` in `client/src/docs.ts`: under the lock of its column doc's `title` section, from the cards loaded under that lock, never from cards it loaded before (D-116).
- A draft's `related` ids are only ones the brief held: its cards, the decisions the team holds and the open pull requests the plugin listed; the page drops a card or decision it cannot find (D-116).
- Only the project's owner links its board: the link is the `repo` of the Roadmap doc's sealed title, and the page and the agent count it only when the owner wrote that title; the agent copies only boards of projects its owner owns, and one board per repository (D-117).
- A board's copy is `copyOf` in `shared/board.ts`, for Copy as Markdown and for the agent alike, of each Roadmap card's text that stands: the agent reads the Roadmap from `GET /docs/:id/words` through `cardsOf`, with the project's members now, as the page does; the agent pushes only `agent/board`, never forced, writing the two docs and removing the proposal files its owner added (D-117, D-092).
- A Bark push carries chat name, sender name, urgency and unread count, never message text; one APNs provider token is shared through the database and refreshed at most every 20 minutes (D-054).
- The Bark key comes from `BARK_APNS_KEY` and is never committed (D-054).
- An agent is a member account that never makes keys; it keeps its secrets in the role account's folder (`/var/webchat`, `/var/lib/webchat`), one copy for the laptop under `laptop/`, behind the one `watch.lock` that the serving keyholder holds (D-085, D-094, docs/decisions/locked-room.md).
- The keyholder (`agent/index.ts keyholder`) is the one host of `Plugin`, and `dev` runs it with a runner in one process; `plugin.ts` never names a harness or a command of its host, and `serve`, `pair <code> <name>` and the plugin's server are gone (docs/decisions/one-daemon-host.md).
- An agent checks in every 15 seconds, and every 60 once an hour passes with no request, run or turn (`checkInEvery`); the server counts an agent online for 2 minutes after a check-in, a person for 1, in `toUserDTO` and in the fingerprint alike (docs/roadmap/new-agent-setup.md).
- `webchat-agent setup` checks the administrator rights first and stops before it changes anything; its other checks are read-only, and it changes something only after its one question, asked on `/dev/tty`, since the line runs under `curl … | sh` and stdin is the script (docs/decisions/agent-install.md).
- Setup never changes a security setting: for WSL2 without systemd, and for Ubuntu's AppArmor rule on user namespaces, it prints the fix, and it installs only git, the sandbox's `bubblewrap` and `socat`, and the harness's own installer (docs/decisions/agent-install.md).
- Setup pairs before it installs anything, since a pairing code lapses after 10 minutes and Apple's installer can take longer; a run with no code pairs nothing and replaces the services (docs/roadmap/new-agent-setup.md).
- The runner's login service runs `<installed program> runner` with the PATH an interactive login shell has, read between markers so a profile's output cannot spoil it; a value in a unit or a plist goes through `systemdUnit` or `launchdPlist`, which escape `%`, `$` and XML (docs/roadmap/new-agent-setup.md).
- An agent's account comes only from pairing: the code stays in the page and the agent, the server sees its SHA-256 and HMAC proofs, and each side pins the keys the code proved (D-093).
- Run requests, reports and cancels are messages whose sealed `run` field names the card or the request's message id; a page folds only reports from the agent the request names, and an agent heeds only its owner's cancel (D-086, R-030).
- A card's run state comes from the user's run messages in their chats with their agents; its status line follows from any page of theirs, under the card's lock, once per report: Running on claimed, Waiting for a decision on decision, In review on done, Done or Fixed on merged, its old status back on failure, stale or a draft closed unmerged; a card that still says `In progress: Ann’s agent` reads as `Running: Ann’s agent`, and a request's older `was` goes through `newStatus`, so a run in flight across the change still moves (D-100, D-105, D-118).
- The brief refuses a card whose status shows someone else's agent `Running:`, `In review` or `Waiting for a decision`, the only run state teammates see (K-59, D-100, D-118).
- A card run refuses a card an open pull request claims; its first turn checks the card and commits nothing; only then do an empty claim commit and the draft open, before any code (D-118).
- With the plan gate on, the default, a card that holds reports `planned` with the check's plan and waits in `plans.json`, before the claim commit, for the owner's `fix`: a go or their words; a stop or 7 days end it. Only `noPlan` in the setup choice skips it, and only for a harness whose adapter declares the knob (docs/decisions/redirect-plan-gate.md).
- A run that fails or waits 7 days before its work is done closes its draft with a comment and keeps its branch; a merge accepts only the Proposed decisions the run named that its board holds (D-118).
- A stop before the work is done pauses the run instead: what is committed is pushed, and the worktree, branch, draft and session stay in `pulls.json` as `unfinished.paused` with `stopped`; the owner's `fix` with a note resumes the session with their words fenced, as teammates' text is, and a second stop closes the draft (docs/decisions/stop-pauses-run.md).
- A run's progress reaches the owner as sealed `progress` reports, one sentence from the adapter at most every 30 seconds and only when it changed, never the harness's output itself; the service worker shows no notification for one, except on Safari (docs/decisions/stop-pauses-run.md, D-047).
- An agent runs a request only when its owner sent it, verified against the pinned keys, with a signed send time within 10 minutes of its own clock, and the hash of the brief they saw: the card, then the decisions without the superseded ones, as `briefText` makes it on both sides (D-089, D-105).
- An agent acts on a request's signed client id once; it remembers ids on disk while a copy could still run (K-47, D-093).
- An agent pins a person's changed keys only on its owner's signed `trust` message in their direct chat, for the fingerprint the server shows now and newer than the last check it pinned; whatever makes the page pin changed keys must send it to the owner's agents too, or their briefs hash differently (D-110, K-57).
- An agent answers a second request for the card it is running with one failed report and starts nothing; a card is the board's doc and section, a run that ended no longer counts, and another card runs beside it, with no cap (K-51, D-099, R-037).
- The owner names the harness, signed, in each run request and prompt, from the sealed setup answer's list; the keyholder keeps no default, runs a request that names none on the first harness the owner linked, fails one naming a harness that is not linked with the reason, and resumes every reply and fix round with the harness that started the session, which `Conversation` and `Watched` record by name (docs/decisions/new-harness-pick.md).
- Only a harness the owner linked runs: `SetupChoice.linked`, in the order they linked, minus the older `off`, which a page from before linking still writes and which the merge in `setupOnWord` keeps; the first start of an agent with no `linked` links what it found minus `off`, and nothing later links itself (docs/decisions/harness-linking.md).
- The check-in's level is `answers | setup`, plus `cards` from `noHarness()` over the linked harnesses alone, so with none linked it keeps the first two and every request fails with `NONE_LINKED`; test an empty list apart, since `every` is true for it (docs/decisions/harness-linking.md).
- The picks at pairing are one `picks` field sealed under a key from the pairing code, with the agent's keys as its AAD; the server never holds a harness name, and the agent writes `linked` only once the owner approved (docs/decisions/harness-linking.md).
- A request from `webchat-agent link` or `connect` is a request over the keyholder's socket, which it files in `asks/` and sends as a sealed `ask`: a file older than 10 minutes, a name outside `SUPPORTED`, and a second request for what waits are dropped, and the approval acts only on what the agent recorded for that client id, on the owner's word in their direct chat, signed within 10 minutes, once; the next `ask` kind adds a variant of the same field (docs/decisions/harness-linking.md).
- The finder looks only in absolute folders: the PATH the process has and a few in the home folder; a relative one would be a place the model writes (D-097, docs/decisions/harness-linking.md).
- A harness adapter refuses a version below its minimum from one `--version` read per adapter, which the finder rebuilds when the program or its mtime changes; Claude Code's is 2.1.259, the first with `--permission-prompts` and `--permission-prompt-tool`, and Codex has none (docs/decisions/harness-linking.md).
- The agent runs a request only in the folder whose origin is the request's signed `repo`, and refuses a folder whose origin's https address holds a login, which a shell could read from `.git` (D-093, D-094, D-097).
- The harness's turn fails after 2 hours with no output, which does not run while a question waits for the owner (`Quiet`, `watchdog`); the board stops waiting on a request no agent answers after 30 minutes (D-097, D-100).
- The agent works only in a folder that a `connected` mark in the keyholder's folder names, while it is a checkout of that repository, which the runner confirms; only the owner's signed clone and signed connect approval write a mark (D-101).
- `webchat-agent card` sends only a new card's file, checked by a turn as a prompt's drafts are, as a sealed `proposal` draft to the owner; only the owner's `added` note gives it its number, and the command waits for that note and never writes the board (R-044, D-104, D-116).
- `webchat-agent connect` never writes a mark: it files a request, and the approval must repeat the repository and folder the owner saw and arrive within 10 minutes of the agent sending it, the agent's clock, or it changes nothing (the connect-approval decision, proposed in #202).
- The keyholder clones only on its owner's signed clone message, in their direct chat, within 10 minutes, once; only a repository a project of the owner and the agent links; into its own full clone first, and the runner makes `~/WebChat/<owner>/<name>` from a bundle of it, never the harness's turn (D-108).
- For Claude Code, the harness's turn always runs `claude -p --input-format stream-json --restricted`, one process for a session with the plugin's `--settings` file, which the runner writes again before each process starts, since it sits in the owner's folder, which keeps `sandbox.failIfUnavailable`, `permissions.blockReadsOutsideWorkingDirectories` and a `deny` for each credential variable: a plain `-p` run loads the repository's hooks and `.mcp.json`, an unavailable sandbox runs the shell unsandboxed, a sandboxed shell reads the macOS keychain, and it inherits every token in the environment, and Claude Code's `session-env` holds the SessionStart hooks' environment. Never set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` there: it makes every sandboxed command ask (D-097).
- Text a teammate wrote reaches the harness's turn only on its stdin, never in its arguments, which `ps` shows (D-097).
- A harness adapter (`agent/harness.ts`) owns the turn, its warning and the setup it offers; `plugin.ts` never names a harness (docs/roadmap/new-harness-adapter.md).
- An ACP agent runs only from `agent/acp-agents.ts`, whose entries carry a file name (never a path, `npx` or another launcher), the args that make it speak ACP, and the args or environment that skip the owner's settings and MCP servers with a dated check; the list-shape test in `test/acp.test.ts` refuses an entry without them, unless `HARNESS_WARNING` in `shared/types.ts` names it, as for Hermes, whose warning setup, the link approval and Settings show; nothing else may supply a command (docs/decisions/acp-adapter.md, docs/decisions/new-hermes-unconfined.md).
- An ACP turn's text goes only over the protocol, and its answer comes only from `submit_answer`, which `fits` checks against that turn's schema; its permission requests get `judge`'s answer, never an `*_always` option, and what the rulebook cannot decide goes to the owner when the turn can ask (docs/decisions/acp-adapter.md, docs/decisions/harness-approvals.md).
- An adapter that keeps a process for a session ends it after 10 minutes without a turn, in `end(session)` and when the daemon exits; a later turn resumes the session (docs/decisions/acp-adapter.md).
- Every harness may take cards: its adapter's `refusal()` says only why this laptop cannot run it, and `warning()` says what its sandbox lets its shell read, which shows in its row's `attention` and stops nothing. Codex cannot commit, so the runner commits what it left, titled with the answer's title; it runs one `codex app-server` per session with each of the owner's MCP servers off by name (`-c mcp_servers.<name>.enabled=false`; `-c` merges and never replaces), hooks off and `shell_environment_policy.inherit="core"`; its `.rules` still load, and its message goes over the protocol (docs/decisions/harness-rulebook.md, docs/decisions/harness-approvals.md).
- A conversation's messages carry a sealed `prompt` field naming its prompt's client id, never the server's message id; the plugin heeds only its owner's, in their direct chat with the agent, with a signed send time within 10 minutes and once per client id (D-102, D-089, K-47).
- A conversation's turns run in a scratch repository of its own in the temp folder, never a worktree of the owner's checkout, whose `.git` it would share; nothing from it is pushed. A question with no repository runs in an empty folder there, from the board alone (D-102, R-038).
- The keyholder forgets a folder only on its owner's signed `forget` message in their direct chat, and removes its mark, never its files (D-101).
- While the keyholder's `asleep` file exists, it takes no `watch.lock` and starts nothing new; only the owner's signed `sleep` message or `webchat-agent sleep` writes it, and only `webchat-agent wake` removes it. Both commands carry no authority, since any process of the owner can send them (D-113).
- The page asks only a session whose check-in names `AGENT_LEVEL.answers` or above: older agents check in but ignore prompts, so the pane tells their owner how to update instead (D-103).
- A run loads of the owner's Claude setup only what their signed `setup` chose: CLAUDE.md through `--append-system-prompt-file`, and copies of chosen skills, never links in them, in a plugin folder made for the turn that holds only `skills/`; never the owner's settings, hooks, MCP servers, plugins or permission rules. Attribution goes in the object form only, since a `-p` run drops a settings file that fails validation. The level is a set of bits: test cards with `runsCards` and settings with `takesSetup`, never with `>=` (D-115).
- A harness adapter declares a knob only when it honors it with no code outside the sandbox and no change of permission or sandbox mode; permission mode, plugins, hooks and MCP servers are never knobs, for any harness. What a harness is and offers reaches only its owner, sealed in `setupState` (D-115).
- A harness's `refusal` in `setupState` says why it runs nothing, and `answers` says the same; the sandbox warning goes in `attention`, which pages from before linking ignore (docs/decisions/harness-linking.md).
- An agent never writes the board: its card drafts reach it only when the owner's page writes them, and a change only while the card's text still has the hash the draft names (D-104).
- A conversation's brief holds only the board its owner's page named in the signed prompt, never every project the agent is in: anyone can add an agent to their project (D-104).
- Only the keyholder pushes: the run's `agent/*` branch, never forced, and it never merges. The runner's git in a worktree runs through `worktreeGit`, with hooks off and on the git folder the checkout lists, never the worktree's `.git` file, since the worktree's files are the model's (D-092).
- The keyholder's half (`agent/keep.ts`) never runs git in a folder the owner owns: it fetches and pushes only in its own bare clone, with hooks off and credentials only from `gh`, one operation per repository at a time, and what it sends or takes of the owner's folders is a bundle (docs/decisions/locked-room.md).
- A run's work is pushed only after `Keep.acceptBundle` took it: exactly one ref, the run's recorded `agent/` branch, `check-ref-format`, `bundle verify`, its pack taken with `index-pack --strict` rather than fetched, since git before 2.46 ignores `transfer.fsckObjects` for a bundle, the run's base an ancestor, no rewind, at most 512 MiB (docs/decisions/locked-room.md).
- The board's copy is committed with git plumbing in a temporary index (`Keep.commitFiles`), never a checkout, so a link in the repository, such as `docs`, cannot lead a write out of the clone (docs/decisions/locked-room.md).
- A run's worktree is under `.claude/worktrees`, where the sandboxed shell may write. A run never pushes to main and fails after 2 hours of silence or with no commits (D-092).
- A review by anyone but the owner waits for the owner's `fix` message, which names the review's report: only the text that report showed runs, so nothing posted after the owner looked rides along. The owner's own rounds count toward no limit (D-105).
- The plugin stops watching, when it loads, a draft whose request is not in the owner's direct chat with the agent: the pane builds a card's thread only from that chat, so it shows neither that draft's reviews nor the button that sends the go (K-58, D-105).
- A harness asks the owner only when the request or prompt carries the signed `asks` flag, since an older page never shows a question; without it the adapter starts no approval endpoint or `on-request` policy and refuses, as before. `Turn.ask` rejects only when the run cannot go on, and the adapter then fails the turn with that error (docs/decisions/harness-approvals.md).
- A question is a sealed `permit` in the owner's direct chat; the owner's answer counts once, from the owner, in that chat, within 10 minutes of its signing, for the `seen` hash of what they saw, and a late one says `stale` and leaves the question open. A question waits 7 days by the wall clock in `pollPulls`. The agent allows nothing on its own but a command of a harness whose `sandboxed()` says its shell cannot leave the sandbox, in `LocalBench.turn`, after `judge` passed its paths: `judge` refuses or asks, a grant for this run is exact-match and in memory, and Codex and ACP are never told `acceptForSession`, an amendment or `allow_always` (docs/decisions/harness-approvals.md).
- Claude Code's approval endpoint (`agent/approve.ts`) listens on 127.0.0.1 only, takes a per-process token from a 0600 file in the runner's folder, never from arguments or the environment, refuses a request with an `Origin`, answers one text block with no `structuredContent`, and keeps its held response alive with comments. The tool is hidden from the model with `--disallowedTools` (docs/decisions/harness-approvals.md).
- A question renders as plain text in the pane, never Markdown, since a command can hide in it, and the lock screen shows only "Your agent asks your permission" (docs/decisions/harness-approvals.md).
- Nothing secret crosses the keyholder's socket (`agent/room.ts`) and nothing on it carries authority, since any process of the owner can connect: every reply is checked as data (harness names against `SUPPORTED`, folders against the request, branches and worktrees against the card, answers with `fits`, bundles with `acceptBundle`), and the `approve` the runner sends only reaches the keyholder's own caps and question (docs/decisions/locked-room.md).
- The first runner to say hello keeps the socket; a second is refused while it is open, and a version that differs is refused, except the updater's hello, which skips the check and may ask only `busy`. Lines are capped at 4 MiB, and a transfer id is good once, for 10 minutes (docs/decisions/locked-room.md).
- Pairing never crosses the socket: a code from another WebChat account would make that account the agent's owner. The keyholder shows offline, with no check-ins, while no runner is connected (docs/decisions/locked-room.md).
- The rulebook runs in the runner (`LocalBench.turn`), where the owner's paths resolve; the keyholder's `Permits` only caps, grants and asks (docs/decisions/locked-room.md).
- The keyholder runs only programs that root owns: Apple's command line tools git or `/usr/bin/git`, and the `gh` release that setup pins by SHA-256 in `agent/gh.ts` and installs in the root-owned program folder; its PATH lists only root-owned folders, never Homebrew's (docs/decisions/locked-room.md).
- Setup's root commands write generated content through stdin into a folder only root writes, by a rename (`put`, `putAs` in `agent/lockroom.ts`), never through a file the owner could swap; the program is installed from bytes hashed against the hash setup took at its start; every root command goes through one `Root`, which tests replace (docs/decisions/locked-room.md).
- Only setup's sudo pairs the keyholder: `webchat-agent pair` takes the code and picks on stdin, never in an argument, and refuses to run as anyone but the role account; setup deletes `_webchat` and its groups only when the mark in their full name or comment is its own, and refuses a foreign one. One owner per laptop: `_webchatipc` holds only them (docs/decisions/locked-room.md).
- The keyholder starts only after `selfProblem` (`agent/lockroom.ts`): it runs as the role account, its data folder is its own with mode 700, and its program, `git` and `gh` are root-owned and writable by no one else, up every parent folder; it sets umask 077 (docs/decisions/locked-room.md).
- `status` over the socket answers fields (`AgentStatus`), and `doctor` and setup read them, never the text; a field the agent cannot know yet is left out, not guessed (docs/decisions/locked-room.md).
- The updater (`agent/update.ts`) runs as root from the root-owned program and trusts only what root owns: `update.json`, which setup wrote through stdin, and the release address pinned in `AGENT_RELEASES`, never one the server names. The server only says which release; a release that is not `x.y.z` is refused before any plan is built, and one not newer than the program does nothing (docs/decisions/agent-self-update.md).
- The updater never uses a GitHub login and never opens the role account's files. A download is checked in memory against its `.sha256`, unzipped and probed with `--version` into the program's folder, and renamed into place; a failure keeps the old program and restarts nothing (docs/decisions/agent-self-update.md).
- The updater restarts the keyholder only when it reports nothing running, or after 24 hours busy; it keeps the old program until the new keyholder answers with the new version in 2 minutes, else it puts it back and skips that release. Setup and uninstall stop it first (docs/decisions/agent-self-update.md).
- A run's dev server starts only through WebChat's `dev_server` tool, in the runner, under `devProfile` (`agent/browser.ts`): it binds and reaches only the lab's two ports, writes only the working folder and the lab's temp folder, reads file contents under a home folder, `/Volumes` or a temp folder only in those two and the `node` on PATH's folder (the tool returns its output to the model), reads no secret folder, and gets no DNS, Mach service or signal outside the sandbox; it never runs as a plain process of the owner, and it ends with the turn. Seatbelt matches a socket's path as given and a `unix-socket` filter takes one path, so give real paths, one rule per folder (docs/decisions/new-dev-server-sandbox.md).
- Chrome comes only from chrome-devtools-mcp launching it, never `--browserUrl`, `--wsEndpoint` or `--autoConnect`: headless, `--isolated`, statistics, CrUX, update checks, config discovery and `file:` navigation off, and every request through the lab's proxy with loopback not bypassed, which passes only `onRunPort` addresses (docs/decisions/new-dev-server-sandbox.md).
- `judge` allows a browser tool only from `BROWSER_TOOLS`, by name, and only with a lab; add a tool there only after reading its arguments. `claudeAsk` judges every argument whose name ends in `path` or `paths` as a path, and a `url` passes only through `onRunPort` (docs/decisions/new-dev-server-sandbox.md).
- chrome-devtools-mcp is pinned in `agent/browser.ts` by version and SHA-256, with the same exact version in package.json; setup installs it root-owned in the program folder and a run never fetches it. The single file runs it with `webchat-agent browser`, through `vm`'s main-context loader, since a single executable cannot `import()` a file (docs/decisions/new-dev-server-sandbox.md).
- A run's screenshot reaches the owner only through `send_screenshot`, with a lab: the runner judges the path and puts the bytes on a side connection (`upload`, then `shot`, for a live turn, at most `LIMITS.fileBytes`); the keyholder's `Permits.shot` checks them as data (PNG by its first bytes, IHDR at most `LIMITS.photoPixels`, 12 a run in memory), sends one at a time `SEND_GAP_MS` apart, and tells the model only the fixed `SHOT` sentences (docs/decisions/new-run-screenshots.md).
- A screenshot is an ordinary message with the sealed `file` field and `fileId`, in the owner's direct chat, with a `run` report of kind `note` or a `prompt` of kind `note`, which changes no state; the pane shows a message with a `file` through `FileBubble`, its text as plain text (docs/decisions/new-run-screenshots.md).
